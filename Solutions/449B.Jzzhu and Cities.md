## Problem Overview

There are `n` cities connected by `m` bidirectional roads and `k` train routes. Each road connects cities `a` and `b` with travel time `c`. Each train route goes from city `1` (capital) to city `u` with travel time `v`.

Jzzhu wants to cancel the maximum number of train routes such that the shortest travel time from city `1` to every city remains the same.

**Example:**
- Roads: `1-2 (1)`, `2-3 (2)`, `1-3 (3)`, `3-4 (4)`, `1-5 (10)`
- Trains: `1→3 (1)`, `1→4 (5)`, `1→5 (8)`
- Shortest distances: `dist[3]=1` (train), `dist[4]=5` (train), `dist[5]=8` (train? or road 1-5=10? train=8 is shorter), `dist[2]=1` (road)
- Wait, with trains: `1→3` cost 1, then `3→4` cost 4 → city 4 costs 5. Train `1→4` also costs 5. So both give `dist[4]=5`. Road path to 4: `1-2-3-4 = 1+2+4 = 7`. So train to 4 can be cancelled because train `1→3` + road `3-4` gives the same shortest distance 5.
- Train `1→3` cannot be cancelled because it gives `dist[3]=1` and the only other path to 3 is road `1-3` cost 3 (longer) or `1-2-3` cost 3 (longer).
- Train `1→5` cost 8: road `1-5` cost 10 is the only other. So train to 5 must stay.
- Answer: 1 cancellation (train to 4).

Note: the sample from the statement gives output 2, meaning two trains can be cancelled in that specific input. The example above is a custom explanation.

## How the condition was analyzed

1. **`n` up to `10^5`, `m` up to `3·10^5`, `k` up to `10^5`** — this requires an `O((n + m + k) log n)` algorithm. Dijkstra is the natural candidate.
2. **Train routes are just additional edges** — a train from `1` to `u` with time `v` can be modeled as an undirected edge `(1, u, v)` in the graph. If the problem allows only `1 → u`, the edge is still usable in both directions for shortest paths (because if you can go from 1 to u in time v, you can also go from u to 1 in the same time in an undirected sense — but Dijkstra only cares about reachability from the source).
3. **Maximize cancelled trains = minimize kept trains** — we need to select the smallest set of train routes that, together with all roads, preserves all shortest distances. The rest can be cancelled.
4. **Key insight: build a shortest-path tree and prefer roads over trains** — during Dijkstra, whenever we can reach a city `v` through multiple shortest paths, we should remember a path that uses a road, not a train, if possible. This way, the remembered parent edge for `v` is a road if any road shortest path exists; otherwise, it is a train. The set of remembered train edges is the minimum set of trains we must keep.

## Algorithm Explanation

### Step 1: Build the graph

- Roads are stored as edges with `train = false`.
- Each train route is stored as two directed edges (or undirected) between `1` and `u` with `train = true`.
- We need to distinguish road edges from train edges, so each edge stores a `bool train` flag.

### Step 2: Dijkstra from city 1

Run Dijkstra using **all** edges (roads + trains). This gives `dist[u]` — the shortest time from city `1` to city `u` in the full graph.

During Dijkstra, maintain `par[u]` — the ID of the edge through which we first (or best) reached `u`.

### Step 3: Prefer roads over trains when distances are equal

This is the critical part. When we relax an edge `(u, v, w)`:

- If `dist[u] + w < dist[v]`: we found a strictly shorter path to `v`. Update `dist[v]` and set `par[v]` to this edge.
- If `dist[u] + w == dist[v]`: we found an alternative path with the same length. If the current `par[v]` is a train and the new edge is a road, replace `par[v]` with the road. If the current `par[v]` is a road, keep it. If both are the same type, it does not matter for the count.

### Why preferring roads is correct

For each city `v`, `par[v]` is an edge that lies on **some** shortest path from `1` to `v`. We want `par[v]` to be a road if possible. The set of all `par[v]` forms a shortest-path tree (more precisely, a shortest-path arborescence) that preserves all distances.

If `par[v]` is a road, city `v` does not need any train. If `par[v]` is a train, that particular train is necessary to maintain `dist[v]` — but only this one. All other trains to `v` (or other cities) are redundant.

The number of train edges in this parent array is exactly the minimum number of train routes we must keep. Therefore:

```
answer = k - (number of cities v where par[v] is a train)
```

### Why a naive per-city count can fail

At first glance, one might think: for each city `u`, count how many train routes reach it with length `dist[u]`. If more than one, cancel all but one. If a road also gives `dist[u]`, cancel all trains. This is wrong.

**Counterexample:**
- Roads: `1-2 (3)`, `2-3 (5)`
- Trains: `1→2 (3)`, `1→3 (8)`
- `dist[2] = 3` (road or train), `dist[3] = 8` (train) or `3+5 = 8` (road).
- Both road and train give `dist[3] = 8`. Naive per-city count would say: cancel train `1→3` because a road gives the same distance. But if we cancel `1→3` and also cancel `1→2` (because road `1-2` gives the same `dist[2] = 3`), then `dist[3]` becomes `8` only if `1→2` is kept. Wait, in this case road `1-2` kept, then `dist[3] = 3 + 5 = 8`. So it works.

A better counterexample:
- Roads: `1-2 (3)`, `2-3 (1)`
- Trains: `1→2 (3)`, `1→3 (4)`
- `dist[2] = 3` (road or train), `dist[3] = 4` (train) or `3+1 = 4` (road).
- Naive: city 2 has road, so cancel train `1→2`. City 3 has road, so cancel train `1→3`. But if we cancel both trains, `dist[3] = 3 + 1 = 4` (road) — still works. Hmm.

The real issue is global consistency. Consider:
- Roads: `1-2 (3)`, `2-3 (100)`
- Trains: `1→2 (3)`, `1→3 (4)`, `1→2 (3)` (duplicate train)
- `dist[2] = 3` (road or train), `dist[3] = 4` (train) or `3+100 = 103` (road).
- Naive per-city: city 2 has road + 2 trains with `dist[2] = 3`. Cancel one train, keep one. City 3 has only train with `dist[3] = 4`. Keep it. Total cancel = 1.
- But if we keep train `1→2` (3) and train `1→3` (4), can we cancel the other train `1→2` (3)? Yes. But can we also cancel train `1→2` (3) and rely on road `1-2` (3)? Then `dist[2] = 3`, `dist[3] = 4` via train. Yes, that works too. So we can cancel both trains to city 2, total cancel = 2.
- Naive per-city fails because it only checks `road_cnt[u] > 0` locally and does not recognize that the kept train to city 2 can be replaced by the road while still preserving `dist[3]` through the kept train to city 3.

The Dijkstra parent-preference approach handles this correctly: it builds a global shortest-path tree where for each city we pick the best parent. If road `1-2` can be the parent of city 2, then the train to city 2 is not needed. City 3's parent is the train `1→3`. The tree `1 → 2 (road) → ...` and `1 → 3 (train)` is consistent.

## Algorithm Steps

1. Read `n, m, k`.
2. Read `m` roads, store as edges with `train = false`, add to adjacency list in both directions.
3. Read `k` train routes, store as edges with `train = true`, add to adjacency list in both directions from city `1`.
4. Run Dijkstra from city `1`:
   - Maintain `dist[]` and `par[]`.
   - On relaxation with equal distance, prefer road over train.
5. Count cities `v` (`v = 2..n`) where `par[v]` is a train. Let this count be `used_trains`.
6. Output `k - used_trains`.

## Code

```cpp
#include <iostream>
#include <vector>
#include <queue>
#include <climits>
using namespace std;

typedef long long ll;

struct Edge {
    int v;
    ll w;
    bool train;
};

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(NULL);

    int n, m, k;
    cin >> n >> m >> k;

    vector<vector<pair<int, int>>> adj(n + 1);
    vector<Edge> edges;

    auto add_edge = [&](int u, int v, ll w, bool train) {
        int id = edges.size();
        edges.push_back({v, w, train});
        adj[u].push_back({v, id});
    };

    for (int i = 0; i < m; i++) {
        int u, v;
        ll w;
        cin >> u >> v >> w;
        add_edge(u, v, w, false);
        add_edge(v, u, w, false);
    }

    for (int i = 0; i < k; i++) {
        int s;
        ll y;
        cin >> s >> y;
        add_edge(1, s, y, true);
        add_edge(s, 1, y, true);
    }

    vector<ll> dist(n + 1, LLONG_MAX);
    vector<int> par(n + 1, -1);
    dist[1] = 0;

    priority_queue<pair<ll, int>, vector<pair<ll, int>>, greater<>> pq;
    pq.push({0, 1});

    while (!pq.empty()) {
        auto [d, u] = pq.top();
        pq.pop();
        if (d > dist[u]) continue;

        for (auto [v, id] : adj[u]) {
            ll nd = d + edges[id].w;
            if (dist[v] > nd) {
                dist[v] = nd;
                par[v] = id;
                pq.push({nd, v});
            } else if (dist[v] == nd) {
                // Prefer road over train for the parent edge
                if (par[v] == -1 || (edges[par[v]].train && !edges[id].train)) {
                    par[v] = id;
                }
            }
        }
    }

    int used_trains = 0;
    for (int i = 2; i <= n; i++) {
        if (par[i] != -1 && edges[par[i]].train) {
            used_trains++;
        }
    }

    cout << k - used_trains << "\n";

    return 0;
}
```

## Complexity

### Time Complexity

- Building the graph: `O(n + m + k)`
- Dijkstra: `O((n + m + k) log n)` — each edge is pushed at most once to the priority queue
- Final count: `O(n)`
- Total: `O((n + m + k) log n)`

For the maximum constraints `n = 10^5`, `m = 3·10^5`, `k = 10^5`, this is about `5·10^5` operations with `log n ≈ 17`, well within the 2-second time limit.

### Space Complexity

- Graph: `O(n + m + k)` edges, each stored twice → `O(n + m + k)`
- `dist`, `par`, `priority_queue`: `O(n)`
- Total: `O(n + m + k)` — around `10^6` edges, each edge is an `int` and a `long long`, so roughly 16 MB, within 256 MB.

## Insights and Notes

### Why the answer is not just "cancel trains with v > dist[u]"

A train with `v > dist[u]` is definitely not used in any shortest path, so it can always be cancelled. But a train with `v == dist[u]` may or may not be cancellable, depending on whether there is another shortest path to `u` not using this train. The Dijkstra parent-preference approach handles both cases automatically.

### Why trains are added as undirected edges

Although the statement says a train route goes from `1` to `u`, for Dijkstra from source `1` the direction does not matter. We only need to know that `1` and `u` are connected with time `v`. When relaxing from `1`, we can reach `u`. When relaxing from `u`, we could theoretically reach `1`, but `dist[1] = 0` is already fixed, so it does not change anything. Thus, adding two directed edges `(1, u)` and `(u, 1)` is safe.

### Why `par[v] == -1` can happen

The problem guarantees that every city is reachable from the capital, so `par[v] == -1` should not happen for `v >= 2` in a valid input. The check is just defensive.

### Why preferring the road in the equal-distance case is enough

We do not need to track all shortest paths. We only need, for each city, at least one shortest path whose last edge is a road if possible. By preferring roads in the equal-distance tie, we ensure `par[v]` is the "cheapest" parent in terms of train usage. If a road parent exists, Dijkstra will eventually find it (because all edge weights are positive and Dijkstra explores in increasing distance). When it finds it, `par[v]` is updated from a train to a road.

### What if multiple road edges give the same `dist[v]`?

Then `par[v]` will be one of them. It does not matter which road, because no train is needed for `v`. The answer depends only on whether `par[v]` is a train, not on which specific road.

### Common mistakes

- **Per-city independent count**: counting `road_cnt[u]` and `train_cnt[u]` per city and deciding cancellation locally. This fails due to global dependencies between cities (as shown in the counterexample).
- **Forgetting to add train edges in both directions**: if the edge is only added from `1` to `u`, the adjacency list at `u` will not have the train, and Dijkstra cannot use it to reach `1` (which is harmless here, but consistent with the edge being undirected).
- **Using `int` for distances**: `c` and `v` can be up to `10^9`, and the sum along a path can exceed `2·10^9`, overflowing `int`. Use `long long`.
- **Treating the problem as "cancel any train with `v >= dist[u]`"**: `v == dist[u]` is not automatically cancellable if this train is the only shortest path to `u` and to cities reachable through `u`.

### Related concepts

- **Shortest path tree (SPT)** — a tree formed by one shortest path from the source to each vertex
- **Dijkstra with parent tracking** — Dijkstra that remembers the predecessor edge, used for path reconstruction or edge analysis
- **Graph edge removal while preserving shortest paths** — a family of problems where one must find redundant edges in shortest path structures

### Why this problem is rated 2000

- The Dijkstra part is standard.
- The non-trivial part is recognizing that train routes are just edges and that the problem reduces to finding a shortest-path tree with a minimum number of train edges.
- The equal-distance tie-breaking (prefer road over train) is the key insight that transforms the problem into a single Dijkstra run.
- Many competitors try the naive per-city count and fail on global-dependency cases.

### Why this approach and not alternatives

**Why not run Dijkstra `k` times, once without each train?**
This would be `O(k · (n + m + k) log n)`, which is `O(10^5 · 10^5 log 10^5)` — far too slow.

**Why not check each train independently (one-by-one cancellation)?**
As shown in the counterexample, a train can be cancellable only if we keep another specific train. If we cancel trains one by one without considering simultaneous effects, we may count trains that cannot all be cancelled together. The problem asks for the maximum number of train routes that can be cancelled simultaneously.

**Why not use a separate set-inclusion test for each subset?**
That would work for small `k` and is exactly what the brute force does. For the real constraints (`k` up to `10^5`), subset enumeration is `O(2^k)` and impossible. The Dijkstra tie-breaking trick is the efficient replacement.
